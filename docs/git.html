🚀Введение

Git — распределённая система контроля версий. Хранит всю историю проекта локально у каждого разработчика, позволяет безопасно экспериментировать и работать в команде.

Три состояния файла

┌──────────────┐   git add    ┌──────────────┐  git commit  ┌──────────────┐
│   Рабочая    │ ───────────► │    Индекс    │ ───────────► │  Репозиторий │
│  директория  │              │  (staging)   │              │    (.git)    │
└──────────────┘ ◄─────────── └──────────────┘ ◄─────────── └──────────────┘
                  git restore                   git reset

📂 Working Tree

Файлы, которые вы редактируете. Изменения здесь ещё не зафиксированы.

📥 Staging Area

«Черновик» будущего коммита. Сюда добавляете то, что войдёт в фиксацию.

🗄️ Repository

Папка .git — вся история коммитов, ветки и теги.

💡

Главное правило: Git почти ничего не удаляет навсегда. Почти любое действие отменяется через git reflog — журнал перемещений указателя HEAD.

⚙️Установка и настройка

Установка

# Windows — скачать установщик с https://git-scm.com/download/win
# macOS (Homebrew)
brew install git

# Debian / Ubuntu
sudo apt update && sudo apt install git

# Проверка версии
git --version

Первичная настройка (обязательно)

# Представиться — данные попадут в каждый коммит
git config --global user.name "Иван Иванов"
git config --global user.email "ivan@example.com"

# Основная ветка по умолчанию
git config --global init.defaultBranch main

# Редактор для сообщений
git config --global core.editor "code --wait"   # VS Code
git config --global core.editor "nano"          # nano

# Прочее
git config --global color.ui auto
git config --global core.autocrlf input   # macOS / Linux
git config --global core.autocrlf true    # Windows
git config --global pull.rebase true      # pull через rebase
git config --global push.autoSetupRemote true  # авто-u при push

# Посмотреть настройки
git config --list
git config --global --list
git config --global --edit

SSH-ключ для GitHub / GitLab

# Сгенерировать ключ (Enter на все вопросы)
ssh-keygen -t ed25519 -C "ivan@example.com"

# Скопировать публичный ключ
cat ~/.ssh/id_ed25519.pub

# Вставить на GitHub: Settings → SSH and GPG keys → New SSH key

# Проверить соединение
ssh -T git@github.com

Подпись коммитов GPG

# Сгенерировать GPG-ключ
gpg --full-generate-key

# Узнать ID ключа
gpg --list-secret-keys --keyid-format=long

# Настроить Git
git config --global user.signingkey ВАШ_KEY_ID
git config --global commit.gpgsign true
git config --global tag.gpgsign true

# Подписать коммит разово
git commit -S -m "подписанный коммит"

# Проверить
git log --show-signature
✅

Проверить настройки: git config --global user.name и git config --global user.email — должны вернуть ваши данные.

📝Основы работы

Индексация

# Добавить в индекс
git add file.txt
git add src/                # папку
git add .                   # всё в текущей папке
git add -A                  # всё, включая удаления
git add *.js                # по маске

# Интерактивно выбирать куски файла (очень полезно!)
git add -p
git add --patch

# Убрать файл из индекса (изменения сохранятся)
git restore --staged file.txt
git reset HEAD file.txt     # старый способ

Коммиты

# Зафиксировать проиндексированное
git commit -m "feat: добавил авторизацию"

# Добавить отслеживаемые и сразу закоммитить
git commit -am "fix: исправил опечатку"

# Коммит с подробным описанием (откроет редактор)
git commit
git commit -v                # + показать diff

# Изменить последний коммит
git add forgotten.txt
git commit --amend -m "новое сообщение"
git commit --amend --no-edit  # не менять сообщение

# Пустой коммит (для CI)
git commit --allow-empty -m "trigger build"

# Указать конкретного автора
git commit --author="Иван <i@e.com>" -m "msg"

# Подписать GPG
git commit -S -m "signed"

История и диффы

# Краткая история
git log
git log --oneline
git log --oneline --graph --all --decorate   # ★ самая полезная
git log -5                                   # последние 5
git log -p                                   # с диффами
git log --stat                               # со статистикой

# Фильтры
git log --author="Иван"
git log --since="2 weeks ago" --until="yesterday"
git log --grep="fix"                         # поиск по сообщению
git log -- path/to/file.txt                  # история файла
git log -S "functionName"                    # когда появилась строка
git log -G "regexp"                          # по регулярке
git log --merges                             # только merge-коммиты
git log --no-merges                          # без merge
git log --first-parent                       # только по main-линии

# Диффы
git diff                     # рабочая копия vs индекс
git diff --staged            # индекс vs HEAD
git diff HEAD                # рабочая копия vs HEAD
git diff main..feature       # между ветками
git diff HEAD~1 HEAD         # между двумя коммитами
git diff --stat              # только статистика
git diff --name-only         # только имена файлов

# Показать коммит
git show a1b2c3d
git show HEAD~1:file.txt     # версия файла в коммите
✅

Хорошее сообщение коммита = тип: что сделано. Например: feat: добавил корзину, fix: падение при пустом логине, docs: обновил README.

🧭Навигация по коммитам

Git позволяет ссылаться на коммиты относительно HEAD — «ревизионные выражения».

СинтаксисЗначение
HEADТекущий коммит
HEAD~11-й родитель (предыдущий коммит)
HEAD~33 коммита назад по первой линии
HEAD^1то же, что HEAD~1 — первый родитель
HEAD^2ВТОРОЙ родитель (для merge-коммитов)
HEAD^2~22 назад от второго родителя
HEAD@{2}Где HEAD был 2 «шага» назад (reflog)
main@{yesterday}Где ветка была вчера
@{-1}Предыдущая ветка (git switch -)
v1.0.0Тег
a1b2c3dSHA-1 коммита (можно первые 7 символов)
main..featureКоммиты в feature, которых нет в main
main...featureСимметричная разница
^main featureВ feature, но не в main

Разница ~ и ^

        A --- B --- C  (main)
               \
                D --- E  (feature)
                     \
                      M  (merge = C + E)

M~1 = C (первый родитель)
M^1 = C
M^2 = E (второй родитель)
M^2~1 = D
# Показать разницу между ветками
git log main..feature        # что есть в feature, но нет в main
git log main...feature       # симметричная разница
git log --left-right main...feature   # с указанием стороны
git rev-list --count main..feature    # сколько коммитов

# Разрешить ревизию в SHA-1
git rev-parse HEAD
git rev-parse --short HEAD
git rev-parse --abbrev-ref HEAD       # имя текущей ветки
git rev-parse --verify main           # проверить существование

🌿Ветки и слияние

Просмотр и создание

# Список веток
git branch                 # локальные
git branch -a              # + удалённые
git branch -v              # с последним коммитом
git branch -vv             # + upstream
git branch --merged        # уже слитые в текущую
git branch --no-merged     # не слитые

# Создать ветку
git branch feature/login

# Переключиться (современный способ)
git switch feature/login

# Создать и переключиться
git switch -c feature/login
git checkout -b feature/login      # старый способ

# Переключиться на предыдущую
git switch -
git checkout -

Переименование и удаление

git branch -m new-name             # переименовать текущую
git branch -m old-name new-name    # переименовать любую

git branch -d feature/login        # безопасно (неслитую не удалит)
git branch -D feature/login        # принудительно

git push origin --delete feature/login    # удалить на сервере

Слияние

git switch main
git merge feature/login

# Всегда создавать коммит слияния (сохраняет историю ветки)
git merge --no-ff feature/login

# Только fast-forward (иначе отказ)
git merge --ff-only feature/login

# Отменить merge при конфликтах
git merge --abort

# Octopus merge (несколько веток сразу)
git merge branch1 branch2 branch3

# Squash merge — все коммиты одной кучей
git merge --squash feature
git commit

# Стратегии: "наша" или "их" сторона побеждает
git merge -X ours feature
git merge -X theirs feature
git merge -X ignore-all-space feature
⚠️

Никогда не делайте git push --force в общие ветки (main, develop). Для своих веток используйте --force-with-lease.

⚔️Конфликты глубоко

Конфликты возникают, когда Git не может сам решить, чью версию оставить. Это нормально.

Типы конфликтов

🔀 Merge

Обе ветки меняли одни строки. Решается вручную.

📁 Add/Add

Обе ветки создали файл с одним именем.

🗑️ Modify/Delete

Одна изменила файл, другая удалила.

📛 Rename

Файл переименован по-разному в двух ветках.

Маркеры конфликта

<<<<<<< HEAD
console.log("ваш вариант");
=======
console.error("их вариант");
>>>>>>> feature/login

Разрешение

# Взять свою версию целиком
git checkout --ours file.txt
git restore --ours file.txt

# Взять их версию целиком
git checkout --theirs file.txt
git restore --theirs file.txt

# Открыть mergetool (настраивается)
git mergetool

# Настроить VS Code как mergetool
git config --global merge.tool vscode
git config --global mergetool.vscode.cmd 'code --wait $MERGED'

# Список конфликтующих файлов
git diff --name-only --diff-filter=U
git status --short | grep '^UU'

# Отметить разрешённым
git add resolved.txt
git commit           # Git подставит готовое сообщение

# Отменить операцию
git merge --abort
git rebase --abort
git cherry-pick --abort

☁️Удалённые репозитории

Управление remote

git remote -v                       # список с URL
git remote add origin URL           # добавить
git remote set-url origin NEW_URL   # изменить URL
git remote rename origin upstream   # переименовать
git remote remove origin            # удалить
git remote show origin              # подробно

Отправка

# Первая отправка ветки (запоминает связь)
git push -u origin main
git push -u origin HEAD             # для текущей ветки

# Дальше — просто
git push

# Конкретную ветку
git push origin feature/login

# Все ветки / теги
git push --all
git push --tags
git push origin v1.0.0

# Безопасная перезапись своей ветки
git push --force-with-lease origin feature/login

# Удалить ветку на сервере
git push origin --delete feature/login

# Зеркальная отправка (все ссылки)
git push --mirror

Получение

# Скачать и слить (fetch + merge)
git pull

# Скачать и перебазировать
git pull --rebase

# Только скачать, без слияния — безопасно
git fetch
git fetch origin
git fetch --all

# Удалить ссылки на исчезнувшие ветки
git fetch --prune

# Посмотреть, что скачалось
git log HEAD..origin/main --oneline

Upstream (форк-модель)

# Добавить оригинал как upstream
git remote add upstream https://github.com/ORIGINAL/repo.git

# Синхронизироваться с оригиналом
git fetch upstream
git switch main
git rebase upstream/main
git push origin main

# Подтянуть ветку коллеги
git checkout -b their-work origin/their-branch
ℹ️

fetch vs pull: fetch только скачивает. pull = fetch + merge/rebase. Профессионалы чаще используют fetch, чтобы сначала посмотреть.

↩️Отмена изменений

Файлы

# Вернуть файл к HEAD (ИЗМЕНЕНИЯ ПОТЕРЯЮТСЯ)
git restore file.txt

# Убрать из индекса, изменения оставить
git restore --staged file.txt

# Из конкретного коммита
git restore --source=HEAD~2 file.txt
git restore --source=main file.txt

# Всё локальное
git restore .

Коммиты

# RESET — переписывает историю (опасно для запушенных)
git reset --soft HEAD~1    # отменить коммит, изменения в индексе
git reset --mixed HEAD~1   # (по умолчанию) изменения в рабочей копии
git reset --hard HEAD~1    # УНИЧТОЖИТЬ коммит и изменения  ⚠️

git reset --hard origin/main   # сбросить ветку к серверу

# REVERT — создаёт новый коммит-отмену (безопасно!)
git revert a1b2c3d
git revert HEAD
git revert --no-commit HEAD~3..HEAD   # пачкой одним коммитом
git revert -m 1 <merge-sha>           # отменить merge-коммит

Удаление неотслеживаемых

git clean -n                # посмотреть, что удалится (безопасно)
git clean -f                # удалить файлы
git clean -fd               # + папки
git clean -fdx              # + игнорируемые (например, node_modules)
🚨

git reset --hard и git clean -fd безвозвратно удаляют незакоммиченные изменения. Всегда делайте git stash или git status перед ними.

🧨 reset

Двигает ветку назад, «стирая» коммиты. Только для локальных.

🛡️ revert

Создаёт коммит-отмену. Безопасен для запушенных.

📦Stash — временное хранилище

Позволяет «спрятать» незакоммиченные изменения, чтобы быстро переключиться на другую задачу, а потом вернуть их обратно.

# Спрятать текущие изменения
git stash
git stash push -m "работа над формой логина"
git stash -u                        # включая новые (untracked) файлы
git stash -a                        # включая игнорируемые
git stash push -m "msg" file.txt    # только конкретный файл

# Посмотреть
git stash list
git stash show
git stash show -p stash@{0}         # с диффом

# Вернуть
git stash pop                       # применить и удалить из стека
git stash apply                     # применить и оставить
git stash apply stash@{2}           # конкретный

# Удалить
git stash drop stash@{0}
git stash clear                     # все

# Создать ветку из stash
git stash branch new-feature stash@{0}
✅

Сценарий: правите файл, нужно срочно переключиться. git stash → switch → работа → возврат → git stash pop.

🔀Rebase и cherry-pick

Rebase

«Пересаживает» ваши коммиты на верхушку другой ветки, создавая линейную историю.

git switch feature/login
git rebase main

# После разрешения конфликтов
git add resolved.txt
git rebase --continue

# Пропустить проблемный коммит
git rebase --skip

# Отменить rebase
git rebase --abort

# Интерактивный rebase — последние 3 коммита
git rebase -i HEAD~3

# Перебазировать диапазон на другую базу
git rebase --onto main feature~2 feature

# Перебазировать всю ветку
git rebase --onto main develop feature

Интерактивный rebase: команды

pick   a1b2c3d  feat: добавил кнопку
squash d4e5f6g  fix: опечатка          # объединить с предыдущим
reword h7i8j9k  docs: правка README    # изменить только сообщение
edit   l0m1n2o  wip: временный         # остановиться и изменить
drop   p3q4r5s  мусор                  # удалить коммит
fixup  q6r7s8t  мелкая правка          # squash без сообщения
exec   make test                        # выполнить команду
# можно менять строки местами — изменится порядок

Cherry-pick

# Применить конкретный коммит из другой ветки
git cherry-pick a1b2c3d

# Несколько
git cherry-pick a1b2c3d d4e5f6g

# Диапазон
git cherry-pick a1b2c3d..h7i8j9k

# Без создания коммита
git cherry-pick -n a1b2c3d

# Отменить
git cherry-pick --abort
git cherry-pick --continue
git cherry-pick --skip
⚠️

Золотое правило rebase: никогда не перебазируйте ветки, которые уже кто-то скачал. Rebase переписывает хеши коммитов.

🎯Продвинутый rebase

Fixup + autosquash

Идеальный способ поддерживать чистую историю: правки «приклеиваются» к нужному коммиту.

# Нашли опечатку в старом коммите
git add .
git commit --fixup a1b2c3d

# Или для последнего коммита
git commit --fixup HEAD

# Перебазировать и склеить
git rebase -i --autosquash HEAD~5

# Включить автоматически
git config --global rebase.autosquash true

Разделить коммит

git rebase -i HEAD~3
# Заменить pick на edit у нужного коммита

# Git остановится. Теперь:
git reset HEAD^                 # вернуть изменения в WC
git add part1.txt
git commit -m "feat: часть 1"
git add part2.txt
git commit -m "feat: часть 2"
git rebase --continue

Объединить коммиты (squash)

# Последние 3 в один
git reset --soft HEAD~3
git commit -m "feat: всё вместе"

# Или через interactive
git rebase -i HEAD~3
# заменить "pick" на "squash" у 2-го и 3-го

Автоматический rebase при pull

git config --global pull.rebase true
git config --global pull.ff only       # запретить merge при pull

# Список
git tag

# Лёгкий тег (просто указатель)

🔬Внутреннее устройство Git

Четыре типа объектов

📄 blob

Содержимое файла (без имени). Один контент = один blob.

🌲 tree

Директория: имена файлов и ссылки на blob/tree.

📌 commit

Ссылка на tree, автор, дата, сообщение, родители.

🏷️ tag

Аннотированный тег — объект со ссылкой на коммит.

Структура .git

.git/
├── HEAD              # куда указывает HEAD (ref: refs/heads/main)
├── config            # настройки репозитория
├── description       # для gitweb
├── hooks/            # хуки (примеры .sample)
├── info/
│   └── exclude       # локальный .gitignore (не коммитится)
├── objects/          # все объекты (blobs, trees, commits)
│   ├── pack/         # упакованные объекты
│   └── ab/cdef...    # распакованные (по 2 символа SHA)
├── refs/
│   ├── heads/        # локальные ветки
│   ├── tags/         # теги
│   └── remotes/      # удалённые ветки
├── logs/             # reflog
├── index             # staging area (бинарный)
├── ORIG_HEAD         # состояние до последней опасной операции
└── MERGE_HEAD        # при незавершённом merge

Работа с объектами

# Посмотреть тип объекта

# Посмотреть содержимое
git cat-file -p HEAD
git cat-file -p HEAD^{tree}
git cat-file -s a1b2c3d        # размер в байтах

# Дерево
git ls-tree HEAD
git ls-tree -r HEAD             # рекурсивно

# Создать объекты вручную (plumbing)
git hash-object -w file.txt
echo "hello" | git hash-object --stdin
git mktree
git commit-tree <tree> -m "message"

🪝Хуки (hooks)

Хуки — скрипты, которые Git запускает автоматически до/после событий. Лежат в .git/hooks/.

ХукКогда срабатывает
pre-commitПеред созданием коммита (lint, тесты)
prepare-commit-msgПеред открытием редактора
commit-msgПроверка формата сообщения
post-commitПосле коммита
pre-rebaseПеред rebase (можно запретить)
post-checkoutПосле checkout/switch
post-mergeПосле merge
pre-pushПеред push (запуск тестов)
pre-receive(сервер) перед приёмом push
update(сервер) на каждую ветку
post-receive(сервер) после приёма (CI/CD)

Пример pre-commit

# .git/hooks/pre-commit
#!/bin/sh
if git diff --cached --name-only | xargs grep -l "console\.log" 2>/dev/null; then
  echo "❌ Найден console.log — уберите перед коммитом"
  exit 1
fi
exit 0
chmod +x .git/hooks/pre-commit
ls .git/hooks/*.sample           # примеры

Хуки в команде

# Node.js — Husky
npx husky-init && npm install
npx husky add .husky/pre-commit "npm test"
npx husky add .husky/commit-msg 'npx commitlint --edit "$1"'

# Python — pre-commit framework
pip install pre-commit
pre-commit install
pre-commit run --all-files

# Свой hooksPath (хранить хуки в репозитории)

mkdir .githooks

🔁Rerere — запоминание разрешений

Reuse Recorded Resolution. Git запоминает, как вы разрешили конфликт, и автоматически применяет то же решение.

git config --global rerere.enabled true

git rerere status           # что запомнил
git rerere diff
git rerere                  # вручную применить/записать
git rerere forget file.txt
git rerere gc
✅

Включите один раз — и забудете про повторяющиеся конфликты при rebase.

             \          / \        /

           /              \

        \    /  \  /

main   ●────●────●────●────●
      \  /      \  /

  • Коммитим, пушим, открываем Pull Request.
  • После ревью — merge в main, деплой.

Trunk-Based Development

Все коммитят в main маленькими порциями. Feature-флаги вместо долгих веток.

Fork workflow (open source)

# Форкнуть репозиторий на GitHub
git clone git@github.com:ВАШ_НИК/repo.git
cd repo

git remote add upstream https://github.com/ОРИГИНАЛ/repo.git

git switch -c fix/typo
git add . && git commit -m "fix: опечатка"
git push -u origin fix/typo

# Открыть PR на GitHub

# Синхронизировать
git switch main
git fetch upstream
git rebase upstream/main
git push origin main
ℹ️

Для большинства команд: GitHub Flow. Git Flow — релизы по расписанию. Trunk-based — зрелый CI/CD.

🧹Очистка истории

Иногда нужно удалить файл из всей истории (секрет, большой бинарник). Обычный git rm не поможет.

git filter-repo (современный способ)

# Установить
pip install git-filter-repo
# или: brew install git-filter-repo

# Удалить файл из всей истории
git filter-repo --path secrets.env --invert-paths

# Удалить папку
git filter-repo --path node_modules/ --invert-paths

# По маске
git filter-repo --path-glob '*.pem' --invert-paths

# Заменить текст во всех коммитах
git filter-repo --replace-text replacements.txt
# где replacements.txt: literal:OLD_SECRET==>***REMOVED***

# Переименовать автора
git filter-repo --mailmap mailmap.txt
🚨

filter-repo удаляет origin (защита от случайного push). Добавьте обратно: git remote add origin URL. И предупредите команду — им придётся переклонировать.
